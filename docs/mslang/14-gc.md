# 垃圾回收系统设计

## 概述

mslang 采用**并发三色标记清扫 + 分代回收**的垃圾回收策略，参考 Go 1.8+ 的 GC 实现：

| 属性 | 值 |
|---|---|
| 核心算法 | 三色标记清扫 |
| 并发模型 | 并发 GC（标记/清扫与 mutator 并行运行） |
| 分代策略 | 3 代：Young / Old / Immortal |
| 写屏障 | 混合写屏障（Go 1.8+ 风格） |
| 分配方式 | per-协程 TLAB + Bump 分配 |
| GC 线程数 | 可配置（默认 CPU 核心数） |
| 触发策略 | 堆增长率 + 定时 + 手动 |
| 安全点 | 字节码安全点 |
| 对象布局 | 统一对象头 |
| Finalizer | 支持 `__del__` + C 侧 finalizer |

### 设计目标

- **低延迟**：STW 时间控制在毫秒级以内
- **高吞吐**：GC 开销占总运行时间 < 10%
- **可预测**：避免长时间停顿
- **可调优**：运行时可调整 GC 参数

### 实现路线

| 阶段 | GC 策略 | 说明 |
|---|---|---|
| MVP (Phase 2.5) | STW 标记-清除 + Young 代半空间复制 | 简单实现，无并发 GC |
| 目标 (Phase 7.5) | 并发三色标记清扫 + 分代回收 | 本文档描述的完整设计 |

本文档描述的是**目标架构**（Phase 7.5）。MVP 阶段实现简化版本：Young 代使用半空间复制，Old 代使用 STW 标记-清除（无并发 GC 线程、无写屏障）。Phase 7.5 将在此基础上增量升级为并发 GC。

## 对象内存布局

### 内联小值

`Int`、`Float`、`Bool`、`Nil` 不需要堆分配，直接内联在栈/数组中：

```rust
enum Object {
    Nil,
    Bool(bool),
    Int(i64),
    Float(f64),
    Ref(*mut MsObjHeader),   // 仅引用类型需要堆分配
}
```

内联值的 GC 含义：不需要标记、不需要扫描、不需要回收。

### 堆分配对象

所有需要 GC 管理的引用类型（String、List、Dict、Instance 等）都在堆上分配，带统一对象头：

```
字节偏移:   0         1         2-3       4-7        8-15
         ┌─────────┬─────────┬────────┬─────────┬──────────┐
         │ gc_meta │type_tag │  size  │ padding │class_ptr │
         │  1 byte │ 1 byte  │ 2 byte │ 2 byte  │ 8 byte   │
         └─────────┴─────────┴────────┴─────────┴──────────┘
         │ ← MsObjHeader (16 bytes) → │
                                       ↓ 后续为对象载荷数据
```

**gc_meta 位域**（1 byte）：

```
  7   6   5   4   3        2   1    0
┌───┬───┬───┬───┬───┬───────┬───┬────┐
│age│age│ P │ F │ - │gen(2) │color(2)│
└───┴───┴───┴───┴───┴───────┴───┴────┘
```

| 位 | 字段 | 说明 |
|---|---|---|
| 0-1 | `color` | 三色标记：White(0)、Gray(1)、Black(2) |
| 2-3 | `gen` | 代数：Young(0)、Old(1)、Immortal(2) |
| 4 | `has_finalizer` | 是否注册了 finalizer |
| 5 | `pinned` | 是否被 C 侧 pin（不可移动/不可回收） |
| 6-7 | `age` | 晋升年龄计数 |

**type_tag**（1 byte）：

```rust
#[repr(u8)]
enum TypeTag {
    STRING       = 1,
    LIST         = 2,
    DICT         = 3,
    TUPLE        = 4,
    SET          = 5,
    FUNCTION     = 6,
    CLOSURE      = 7,
    CLASS        = 8,
    INSTANCE     = 9,
    MODULE       = 10,
    ITERATOR     = 11,
    GENERATOR    = 12,
    FUTURE       = 13,
    CHANNEL      = 14,
    BOUND_METHOD = 15,
    JOIN_HANDLE  = 16,
    UPVALUE      = 17,
    EXCEPTION       = 18,
    EXCEPTION_CLASS = 19,
    FILE_HANDLE          = 20,
    NATIVE_C_FUNCTION    = 21,
    LARGE_OBJECT = 0xFF,
}
```

**size**（2 byte）：对象占用的字节总数（含头部），字段容量上限 64KB（u16 最大值）。大对象阈值为 32KB（`LARGE_OBJ_THRESHOLD`）：超过 32KB 的对象进入大对象空间，type_tag 设为 `LARGE_OBJECT`，size 字段置 0（大对象大小由 LOS 单独记录）。

**class_ptr**（8 byte）：指向 Class 元数据（Instance 用）或类型描述表（内置类型用）。内置类型共享静态类型描述表，无需为每个对象存储方法表。

### 类型描述表

每种内置类型有一个静态的类型描述表，包含 GC 扫描所需的元信息：

```rust
struct TypeDescriptor {
    type_tag: TypeTag,
    name: &'static str,
    trace: fn(*mut MsObjHeader, &mut dyn FnMut(*mut MsObjHeader)),
    finalize: Option<fn(*mut MsObjHeader)>,
    size_base: usize,
}
```

`trace` 函数：遍历对象中所有指向其他对象的引用，对每个引用调用回调。GC 标记阶段使用此函数扫描对象。

> **task 40 扩展（CLASS=8 / INSTANCE=9）**：两类堆对象的 TypeDescriptor 已填实：
> - **CLASS**：trace 遍历 `methods` 值（Closure 指针）+ `parent` + `class_attrs` 中的 `Object::Ref`；copy_for_gc 深拷贝 HashMap；forward_fields 修正三组 Ref 槽。
> - **INSTANCE**：trace 遍历 `class` 指针 + `fields` 中的 `Object::Ref`；copy_for_gc 深拷贝 HashMap；forward_fields 修正 class 指针与 fields 槽。
> - **has_finalizer**：含 `__del__` 方法的类，其实例在 `call_class`（实例化）时置 `gc_meta |= HAS_FINALIZER`。finalizer 在 mutator 线程、GC 结束后经 `run_finalizers(&mut VM)` 调用 `__del__(self)`（与 task 39 Generator close_generator 同路径，`gc_disabled = true` 防重入）。

## 堆内存组织

```
MsHeap
├── Young Generation（半空间复制）
│   ├── From-Space（当前分配区）
│   └── To-Space（复制目标区）
│   默认大小：4 MB，动态调整
│
├── Old Generation（标记清扫，free-list 管理）
│   ├── 已分配块（散布在 free-list 中）
│   └── 空闲块链表
│   大小：按需增长
│
└── Large Object Space（大对象单独管理）
    ├── 每个 > 32KB 的对象独立 mmap 分配
    └── 独立回收
```

### Young Generation

采用半空间复制（Cheney 算法）：

- 分为 From-Space 和 To-Space 两个等大区域
- 分配总是在 From-Space 中进行（通过 TLAB 切分）
- Minor GC 时：存活对象从 From-Space 复制到 To-Space，然后交换两个空间
- 优点：无碎片、分配极快（bump pointer）、回收时间与存活对象成正比

### Old Generation

采用标记清扫 + free-list 管理：

- 从 free-list 中分配对象（first-fit 或 best-fit）
- Major GC 时：并发标记清扫，释放不可达对象
- 碎片率过高时触发 Compaction（STW 压缩）

### Large Object Space

- 大于 32KB 的对象直接通过系统 mmap 分配
- 每个大对象有独立的内存页
- 回收时直接 munmap 释放给操作系统
- 避免大对象在 Young 代中频繁复制

## TLAB 分配

### 概念

TLAB（Thread-Local Allocation Buffer）是每个协程私有的分配缓冲区。从 Young From-Space 中切分获得，协程内分配无需任何锁。

### 结构

```rust
struct TLAB {
    cursor: *mut u8,    // 当前分配指针（bump pointer）
    limit: *mut u8,     // TLAB 末尾
    size: usize,        // TLAB 大小
}
```

### 分配流程

```
协程请求分配一个对象（size 字节）
│
├─ size > 32KB ?
│   └─ YES → Large Object Space 分配（系统 mmap）
│
├─ TLAB 剩余空间 >= size ?
│   └─ YES → bump 分配：cursor += size，返回旧 cursor
│            （无锁，仅需一次指针加法）
│
├─ TLAB 剩余空间 < size ?
│   ├─ 从 Young From-Space 申请新 TLAB 块
│   ├─ Young 空间不足 → 触发 Minor GC
│   └─ 新 TLAB 块中 bump 分配
│
└─ 完成
```

```rust
fn alloc_obj(coroutine: &mut Coroutine, size: usize) -> *mut MsObjHeader {
    if size > LARGE_OBJ_THRESHOLD {
        return large_object_space.alloc(size);
    }

    let aligned_size = align_up(size, 8);

    if coroutine.tlab.cursor + aligned_size <= coroutine.tlab.limit {
        let ptr = coroutine.tlab.cursor as *mut MsObjHeader;
        coroutine.tlab.cursor += aligned_size;
        ptr.write(MsObjHeader::new(size));
        return ptr;
    }

    refill_tlab_or_gc(coroutine, aligned_size)
}
```

### TLAB 切分

Young From-Space 被划分为多个 TLAB 块供各协程使用：

```
From-Space (4MB)
┌──────────┬──────────┬──────────┬──────────┬──────────┐
│ TLAB-C0  │ TLAB-C1  │ TLAB-C2  │ TLAB-C3  │  (free)  │
│ (coro 0) │ (coro 1) │ (coro 2) │ (coro 3) │          │
│ 64KB     │ 64KB     │ 64KB     │ 64KB     │          │
└──────────┴──────────┴──────────┴──────────┴──────────┘
```

默认 TLAB 块大小 64KB，协程用完后从 free 区域申请新块。

## 分代回收策略

### 三代设计

| 代 | 名称 | 回收策略 | 回收触发 | 预期频率 |
|---|---|---|---|---|
| Gen 0 | Young | 半空间复制（Cheney） | From-Space 分配失败 | 频繁（毫秒级） |
| Gen 1 | Old | 并发三色标记清扫 | Old 占用率达阈值 | 中等（秒级） |
| Gen 2 | Immortal | 不回收 | 永不 | 无 |

### 晋升规则

对象从 Young 晋升到 Old 的条件：

1. **年龄晋升**：对象经历 `promotion_age` 次 Minor GC 仍然存活 → 晋升到 Old
2. **空间压力**：Minor GC 后 Young 存活量超过 Young 空间 70% → 提前晋升年龄较大的对象
3. **大对象直接进入 Old**：分配时超过 Young TLAB 块大小的对象直接在 Old 分配

### 动态阈值

```rust
struct GcConfig {
    promotion_age: AtomicU32,            // 默认 2，范围 [1, 3]（受 gc_meta 2 位年龄字段限制）
    old_gc_ratio: AtomicF64,             // 默认 2.0（类似 Go GOGC=100）
    young_size: AtomicUsize,             // 默认 4MB，根据 GC 频率调整
    gc_threads: AtomicU32,               // 默认 CPU 核心数
    concurrent_mark_threshold: AtomicF64, // 默认 0.8（Old 占用 80% 时开始并发标记）
    minor_gc_interval_ms: AtomicU64,     // 默认 0（仅在空间不足时触发）
    major_gc_interval_ms: AtomicU64,     // 默认 5000（最多 5 秒一次 Major GC）
}
```

**自适应调整规则**：

| 指标 | 调整 |
|---|---|
| Minor GC 频率 > 10次/秒 | `young_size` 翻倍（上限 64MB） |
| Minor GC 频率 < 1次/10秒 | `young_size` 减半（下限 1MB） |
| Old 代碎片率 > 30% | 触发 Old 代 Compaction |
| Major GC STW > 10ms | 增加 `gc_threads`（上限 CPU 核心数） |
| 晋升率 > Young 存活量 50% | `promotion_age` +1（上限 3） |

## Minor GC（Young 代回收）

### 流程

```
1. STW（暂停所有协程，通过安全点机制）
2. 扫描根集中指向 Young 的引用：
   ├── 所有协程栈中的 Ref 类型
   ├── 全局变量
   ├── C Root 注册表
   └── Remembered Set（Old → Young 的 dirty cards）
3. 存活对象从 From-Space 复制到 To-Space
   ├── 更新所有指向该对象的引用
   ├── 对象年龄 age += 1
   └── age >= promotion_age → 复制到 Old 代
4. 交换 From-Space / To-Space
5. 重置所有 TLAB（指向新 From-Space）
6. 恢复所有协程
```

### Remembered Set

Old 代对象可能持有 Young 代对象的引用（如老列表中 push 了新对象）。Minor GC 必须能找到这些跨代引用。

**Card Table 方案**：

将 Old 代内存按 512 字节为一组划分为 Card。每个 Card 对应 1 byte 的标记：

```
Old Generation Memory
┌─────────┬─────────┬─────────┬─────────┐
│ Card 0  │ Card 1  │ Card 2  │ Card 3  │
│ dirty   │ clean   │ dirty   │ clean   │
└─────────┴─────────┴─────────┴─────────┘

Card Table: [0x01, 0x00, 0x01, 0x00, ...]
```

**写屏障维护**：当 Old 代对象写入 Young 代引用时，标记对应 Card 为 dirty。Minor GC 时仅扫描 dirty Card 中的对象。

## Major GC（Old 代回收 — 并发三色标记清扫）

### 三色标记抽象

- **白色**：尚未被标记的对象（GC 结束后白色对象被回收）
- **灰色**：已被标记但引用尚未被扫描的对象
- **黑色**：已被标记且引用已被扫描的对象

**不变性**：黑色对象不会直接指向白色对象（由写屏障保证）。

### GC 状态机

```
                    ┌──────────┐
                    │   Idle   │◄─────────────────────────┐
                    └────┬─────┘                          │
                         │ 触发条件满足                   │
                         ▼                                │
                    ┌──────────┐                          │
             STW ──►│   Init   │                          │
                    └────┬─────┘                          │
                         │ 扫描根集                       │
                         │ 开启混合写屏障                 │
                         │ 启动 GC Worker 线程            │
                         │ 恢复 mutator                   │
                         ▼                                │
                    ┌──────────┐                          │
                    │Concurrent│                          │
                    │   Mark   │◄── mutator 继续运行      │
                    └────┬─────┘   （写屏障保持不变性）   │
                         │ 灰色队列为空                   │
                         ▼                                │
                    ┌──────────┐                          │
             STW ──►│  Mark    │                          │
                    │  Term.   │                          │
                    └────┬─────┘                          │
                         │ 重扫所有协程栈                 │
                         │ 处理剩余灰色对象               │
                         │ 关闭写屏障                     │
                         ▼                                │
                    ┌──────────┐                          │
                    │Concurrent│                          │
                    │  Sweep   │◄── mutator 继续运行      │
                    └────┬─────┘                          │
                         │ 清扫完成                       │
                         ▼                                │
                    ┌──────────┐                          │
                    │Finalize  │── 执行 pending finalizers│
                    └────┬─────┘                          │
                         │ 更新 GC 统计                   │
                         │ 动态调整阈值                   │
                         └────────────────────────────────┘
```

### 阶段 1: Init（STW，极短）

1. 请求所有协程到达安全点
2. 扫描所有根集（协程栈、全局变量、C roots、模块缓存），标记为灰色
3. 开启混合写屏障
4. 启动 GC Worker 线程
5. 恢复所有 mutator 协程

STW 时间：与根集大小成正比，通常 < 1ms。

### 阶段 2: Concurrent Mark（并发）

GC Worker 线程并发执行：

```
while let Some(obj) = gray_queue.pop() {
    // 1. 扫描对象的所有引用（调用类型描述表的 trace 函数）
    trace(obj, |child| {
        if child.color() == White {
            child.set_color(Gray);
            gray_queue.push(child);
        }
    });

    // 2. 对象扫描完毕，标记为黑色
    obj.set_color(Black);
}
```

此时 mutator 继续运行，通过混合写屏障保持三色不变性。

### 阶段 3: Mark Termination（STW，极短）

1. 请求所有协程到达安全点
2. 重新扫描所有协程栈（并发标记期间栈可能被修改）
3. 处理写屏障产生的剩余灰色对象
4. 关闭混合写屏障
5. 恢复所有 mutator

STW 时间：与协程栈大小成正比，通常 < 0.5ms。

### 阶段 4: Concurrent Sweep（并发）

GC Worker 线程遍历 Old 代堆：

```
for obj in old_generation.iter() {
    match obj.color() {
        White => {
            if obj.has_finalizer {
                pending_finalizers.push(obj);
                obj.set_color(Gray); // 保留到 finalize 执行
            } else {
                free(obj); // 释放内存
            }
        }
        Black | Gray => {
            obj.set_color(White); // 重置，为下次 GC 准备
        }
    }
}
```

**新分配对象在并发标记期间标记为黑色**，避免被误回收：

```rust
fn alloc_during_gc(coroutine: &mut Coroutine, size: usize) -> *mut MsObjHeader {
    let obj = alloc_obj(coroutine, size);
    if gc_phase == GcPhase::Sweep {
        obj.set_color(Black); // Sweep 阶段新分配的对象直接标黑
    }
    obj
}
```

### 阶段 5: Finalize（mutator 线程）

GC 结束后，由 mutator 线程（而非 GC 线程）执行 pending finalizers：

```
for obj in pending_finalizers.drain() {
    // 1. 执行 __del__（如果存在）
    if let Some(del_method) = obj.class().get_method("__del__") {
        call_method(obj, del_method); // 安全：不在 GC 线程中执行
    }

    // 2. 执行 C 侧 finalizer（如果注册了）
    if obj.c_finalizer.is_some() {
        obj.c_finalizer()(obj);
    }

    // 3. 清除 finalizer 标记，下次 GC 可正常回收
    obj.set_has_finalizer(false);
    obj.set_color(White);
}
```

## 混合写屏障

### 原理

混合写屏障（Hybrid Write Barrier）结合了插入屏障和删除屏障的优点，Go 1.8+ 采用此方案：

- **插入屏障**：新写入的引用指向白色对象时，将目标标灰
- **删除屏障**：被覆盖的旧引用指向白色对象时，将旧值标灰

混合写屏障同时做两件事，使得**栈不需要写屏障**（栈始终视为灰色集合的一部分），从而极大缩短 Mark Termination 阶段的 STW 时间。

### 实现

```rust
fn write_barrier(heap: &Heap, slot: *mut *mut MsObjHeader, new_val: *mut MsObjHeader) {
    if !heap.gc_phase.is_concurrent_mark() {
        *slot = new_val;
        return;
    }

    let old_val = *slot;
    if !old_val.is_null() && (*old_val).color() == White {
        (*old_val).set_color(Gray);
        heap.gray_queue.push(old_val);
    }
    if !new_val.is_null() && (*new_val).color() == White {
        (*new_val).set_color(Gray);
        heap.gray_queue.push(new_val);
    }

    *slot = new_val;
}
```

### 写屏障插入点

| 字节码 | 需要写屏障？ | 原因 |
|---|---|---|
| `STORE_LOCAL` | 否 | 栈变量，三色不变性保证 |
| `STORE_UPVALUE` | 是 | 闭包是堆对象，修改其 upvalue 影响堆 |
| `SET_ATTR` | 是 | Instance 字段是堆数据 |
| `SET_INDEX` | 是 | List/Dict 元素是堆数据 |
| `STORE_GLOBAL` | 否 | 全局表在 Mark Termination 阶段统一重扫描 |
| `LIST_PUSH` | 是 | List 元素写入 |
| `DICT_SET` | 是 | Dict 键值写入 |
| `SET_ADD` | 是 | Set 元素写入 |
| `SEND` | 是 | Channel 发送 |

## 字节码安全点

### 原理

安全点是 VM 执行循环中可以安全暂停的位置。并发 GC 需要 STW 时，通过安全点机制让所有协程停下。

### 检查机制

在 VM 执行循环的关键字节码前插入安全点检查：

```rust
fn run(&mut self) {
    loop {
        // 安全点检查：relaxed 原子读，约 1 个 CPU 周期
        if self.vm.safepoint_requested.load(Ordering::Relaxed) {
            self.vm.enter_safepoint(self);
        }

        let opcode = self.read_byte();
        match opcode { /* ... */ }
    }
}
```

### 安全点位置

仅在以下字节码执行前检查：

| 字节码 | 原因 |
|---|---|
| `CALL` | 函数调用前，调用栈清晰 |
| `JUMP` / `JUMP_BACK` | 跳转指令，循环回边 |
| `FOR_ITER` | 循环迭代，保证循环不阻塞 GC |
| `RETURN` | 函数返回前 |
| `IMPORT` | 模块加载（可能触发 IO） |
| `AWAIT` | 协程暂停点 |
| `SEND` / `RECEIVE` | Channel 操作（可能阻塞） |

### STW 协调

```
GC 请求 STW:
  1. safepoint_requested.store(true)
  2. 等待所有协程到达安全点（计数器归零）
  3. 执行 STW 操作（Init 或 Mark Termination）
  4. safepoint_requested.store(false)
  5. 唤醒所有协程

协程到达安全点:
  fn enter_safepoint(coroutine):
    atomic_fetch_sub(&pending_count, 1)
    park_current_coroutine()  // 挂起等待恢复
```

## GC 与协程交互

### 架构

```
┌──────────────────────────────────────┐
│          GC Coordinator              │
│          (独立 GC 线程)              │
├──────────────────────────────────────┤
│  - 管理 GC 周期状态机                │
│  - 协调安全点（请求/等待/恢复）      │
│  - 分配扫描工作给 GC Worker 线程     │
└──────────────┬───────────────────────┘
               │ 分配扫描任务
       ┌───────┼───────┐
       ▼       ▼       ▼
   ┌──────┐┌──────┐┌──────┐
   │GC W0 ││GC W1 ││GC WN │  GC Worker 线程
   └──────┘└──────┘└──────┘  并发扫描/清扫
       ▲       ▲       ▲
       │       │       │
   ┌───┴───┐┌──┴───┐┌──┴───┐
   │Coro 0 ││Coro 1││Coro N│  Mutator 协程
   │ TLAB  ││ TLAB ││ TLAB │  各自独立分配
   └───────┘└──────┘└──────┘  通过安全点/写屏障配合 GC
```

### Minor GC 期间的协程交互

1. GC Coordinator 设置 `safepoint_requested = true`
2. 所有协程在下一个安全点停下，递减 `pending_count`
3. GC Coordinator 等待 `pending_count == 0`
4. 执行 Minor GC（复制存活对象）
5. 更新所有协程栈中的引用（forwarding pointer）
6. 重置所有 TLAB
7. 恢复所有协程

### Major GC 期间的协程交互

1. **Init 阶段**：同 Minor GC，短暂 STW
2. **Concurrent Mark 阶段**：协程继续运行，修改堆引用时触发写屏障
3. **Mark Termination 阶段**：再次 STW，重扫协程栈
4. **Concurrent Sweep 阶段**：协程继续运行，新分配对象标黑

## GC 触发策略

三种触发方式组合使用：

### 1. 堆增长率触发

```rust
// 每次分配后检查
fn check_gc_trigger(heap: &Heap) {
    let live_bytes = heap.old_live_bytes.load(Ordering::Relaxed);
    let allocated = heap.old_allocated_bytes.load(Ordering::Relaxed);

    // 类似 Go 的 GOGC：allocated > live * old_gc_ratio 时触发
    if allocated as f64 > live_bytes as f64 * heap.config.old_gc_ratio() {
        trigger_major_gc(heap);
    }
}
```

### 2. 定时触发

GC Coordinator 线程定期检查：

```rust
fn gc_coordinator_loop(heap: &Heap) {
    loop {
        sleep(heap.config.major_gc_interval_ms());

        if heap.gc_enabled.load() && heap.old_allocated_bytes() > 0 {
            trigger_major_gc(heap);
        }
    }
}
```

### 3. 手动触发

通过 API 或脚本调用：

```c
// C API
msGcCollect(vm, MS_GC_FULL);
```

```ms
# mslang 脚本
import gc
gc.collect()
```

本节描述 GC 系统的**实现风险与缓解策略**，供实现者参考。

### 写屏障自动插入

写屏障不得依赖手动维护清单。编译器在发射以下字节码时统一注入写屏障调用：

- `SET_ATTR`、`SET_INDEX`、`STORE_UPVALUE` — 堆引用写入
- `LIST_PUSH`、`DICT_SET`、`SET_ADD`、`SEND` — 集合元素写入

写屏障实现为 `if gc_phase.is_concurrent_mark() { barrier(...) }` 的内联检查，非 GC 期间零开销。

### 安全点覆盖保证

安全点检查仅在特定字节码（`CALL`、`JUMP`/`JUMP_BACK`、`FOR_ITER`、`RETURN`、`IMPORT`、`AWAIT`、`SEND`/`RECEIVE`）前执行。编译器需**验证**：任何基本块（两个安全点之间的直线代码）不超过 N 条指令（建议 N=1000）。超过阈值的纯计算序列（如大型字面量构造）由编译器自动插入 `NOP_SAFEPONT` 指令。

### unsafe 边界划分

VM 与 GC 大量使用 `unsafe`（`Ref(*mut MsObjHeader)` 裸指针）。要求：

1. **unsafe 边界明确** — `unsafe` 块不超过 30 行，每个块有 `// SAFETY:` 注释说明不变性
2. **debug 模式** — 编译期 `#[cfg(debug_assertions)]` 增加类型标签校验（每次 `Ref` 解引用检查 `type_tag` 合法）
3. **GC 验证工具** — `gc.verify()` 遍历堆检查所有可达对象类型标签一致性，仅在 debug 构建可用

### Phase 7.5 降级路径

并发 GC 作为可配置特性。`gc.set_concurrent(false)` 降级为 STW 标记-清扫（Phase 2.5 行为）。降级开关用于：
- 并发 GC 调试期间
- 单线程嵌入场景
- GC 行为异常时的紧急回退

## 对象生命周期示例

### 典型短生命周期对象

```
时间线:

t0: x = [1, 2, 3]        # Young From-Space 分配（TLAB bump）
t1: print(x)              # 使用
t2: x = nil               # 原列表不再被引用
t3: [Minor GC]            # 列表未存活 → 不复制 → 回收
```

### 晋升到 Old 代

```
t0: cache = {}            # Young 分配
t1: [Minor GC #1]         # cache 存活 → 复制到 To-Space，age=1
t2: [Minor GC #2]         # cache 存活 → age=2 >= promotion_age → 晋升到 Old
t3: [Minor GC #3]         # cache 在 Old 代，不受 Minor GC 影响
```

### 循环引用

```
t0: a = {"ref": nil}
t1: b = {"ref": a}
t2: a["ref"] = b          # a ↔ b 循环引用
t3: a = nil
t4: b = nil               # 循环引用的根断开
t5: [Major GC]            # 并发三色标记：a、b 不可达 → 标记为白色 → 回收
```

### C 侧持有引用

```
C 侧:
  MsValue* obj = msGetGlobal(vm, "config");
  msRoot(vm, obj);             # 注册为 GC root

  # ... GC 可能在此期间运行，但 obj 不会被回收 ...

  msUnroot(vm, obj);           # 注销 root
  # 此后 obj 可能被 GC 回收，不应再访问
```
